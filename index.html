О проекте

Набор инструментов для планируемой миграции протокола резервирования первого хопа с HSRP на открытый VRRP.

Проект решает задачу плановой миграции FHRP на паре ядерных коммутаторов Cisco. Задача типична при переходе на вендор-независимую архитектуру, унификации политики FHRP в смешанной инфраструктуре и подготовке к миграции на сторонние платформы (Arista, Juniper, Huawei, NX-OS), где HSRP либо не поддерживается, либо ограничен.

Инструмент автоматически анализирует две конфигурации (show running-config с ядер core1 и core2), находит общие VLAN, группы HSRP, VIP, приоритеты и track-объекты, определяет роли active/standby по правилам RFC 2281 и генерирует последовательность команд VRRPv2 или VRRPv3 в порядке, минимизирующем простой хостов.

В комплекте — обёртка hsrp2vrrp.py: проверяет окружение (наличие конфигов и дочерних скриптов), отображает интерактивное меню выбора версии и возвращает управление по завершении миграции.

Архитектура и принцип работы

Логика анализа, определения ролей и генерации команд.

Определение active / standby

Алгоритм повторяет правила выбора active-роутера по RFC 2281:

  1. Сравниваются приоритеты standby <g> priority. Выше приоритет — active.
  2. При равенстве (по умолчанию 100) сравниваются IP-адреса VLAN-интерфейсов: большее значение — active.
  3. Если IP-адреса не найдены — core1 считается active по умолчанию.

Такая логика гарантирует преемственность ролей: тот же роутер, что был HSRP-active, становится VRRP-мастером.

Перенос track-объектов

Строки standby <g> track ... анализируются и переносятся без изменения синтаксиса:

  • object-tracking: track 1 decrement 20
  • interface-tracking: track GigabitEthernet0/0 10

В VRRPv2 — на уровне интерфейса; в VRRPv3 — внутри address-family ipv4.

OSPF cost и preempt delay

Для минимизации «перекоса» трафика в переходный период:

  • ip ospf cost 1 для active, 10 для standby
  • vrrp priority 110 / 105
  • preempt delay minimum 180 — защита от флаппинга

Порядок вывода команд

Для каждого VLAN:

  1. Блок standby-ядра — временно становится мастером
  2. Проверка show vrrp brief
  3. Блок active-ядра — возвращает мастер-роль через preempt
  4. Проверка show vrrp / ping VIP

Стратегия миграции

Пошаговый сценарий на один VLAN. Повторяется для каждого VLAN, начиная с наименее критичных.

1

Подготовка (без изменений)

  • Снимок baseline: show standby brief, show ip ospf neighbor
  • Проверка ACL: пропуск IP-протокола 112 на 224.0.0.18
  • Проверка show vrrp brief
  • Согласование окна для критичного сегмента
2

Применение блока Standby

  • Войти на standby-ядро, применить блок
  • show vrrp brief — standby в статусе Master
  • ping <VIP> с хоста — стабильно (1–3 потери)
3

Применение блока Active

  • Войти на active-ядро, применить блок
  • show vrrp brief — active в статусе Master (приоритет 110 > 105)
  • Preempt delay 180 — в течение 3 минут возможен Backup, это ожидаемо
4

Верификация и документирование

  • Роли VRRP совпадают с pre-migration HSRP
  • Все track-объекты Up
  • OSPF-соседство восстановлено
  • Результат зафиксирован в журнале изменений

Не параллелить VLAN

Мигрируйте VLAN поочерёдно. Пакетное применение всех блоков одновременно приведёт к длительному разрыву на всех сегментах.

Проверка и откат

Чек-лист post-migration verification и критерии, при которых обязателен откат.

Чек-лист верификации

Проверка Ожидание
show vrrp briefActive — Master, Standby — Backup
ping <VIP>0% loss после стабилизации
show trackВсе объекты Up
show ip ospf neighborFull/2-Way по ожидаемым интерфейсам
show ip arp <VIP>Виртуальный MAC 0000.5e00.01xx
show vrrp <g>preempt delay 180, ключ (v2) корректен

План отката

Применяется на уже мигрированном VLAN. Обратный порядок: сначала standby, затем active.

interface VlanX
 no vrrp <group> ip <VIP>     ! v2
 ! или
 no vrrp <group> address-family ipv4 ! v3
 standby <group> ip <VIP>       ! вернуть HSRP
 standby <group> priority <исх>
 ip ospf cost <исходный>

Критерии обязательного отката:

  • VIP недоступен > 60 сек после стабилизации preempt
  • Track-объекты Down > 5 минут
  • OSPF-соседство не восстанавливается
  • Потери через VIP > 1% в течение 5 минут

Пример вывода

Фрагмент сгенерированного файла migrate_vrrp2_sequential.cfg

 vrrp 2 authentication md5 key-string MySecretKey

!

Важные замечания

Аутентификация

  • VRRPv2 поддерживает текстовую и MD5-аутентификацию.
  • VRRPv3 не поддерживает аутентификацию (RFC 5798). Компенсируйте ACL/сегментацией.
  • MD5 в VRRPv2 не защищает от перехвата — для критичных сегментов используйте ACL на 224.0.0.18.

Ключи HSRP

Скрипт для VRRPv2 игнорирует исходные ключи HSRP и использует единый ключ, введённый вручную. Длина MD5-ключа до 20 символов.

Виртуальный MAC

VRRP использует 0000.5e00.01xx (HSRP — 0000.0c07.acXX). Возможен кратковременный разрыв. На коммутаторах с port-security/sticky MAC проверьте политику заранее.

Track-объекты

Track-и переносятся в VRRP в том же блоке группы. track не создаёт объект — ссылается на существующий IP SLA / interface. Проверьте, что decrement аналогичен исходному.

OSPF cost и preempt delay

OSPF cost: 1 / 10. Preempt delay 180 сек. Для быстрого DC можно уменьшить до 30–60, для WAN — увеличить до 300–600.

Расположение лаунчера

hsrp2vrrp.py ищет скрипты миграции рядом с собой и в PATH. Держите все три скрипта в одной папке.

Проверка синтаксиса

Синтаксис VRRP может отличаться в зависимости от версии IOS/IOS-XE. Протестируйте на одном VLAN перед массовым применением.

FAQ

Почему команда python не найдена?

Используйте python3 либо установите псевдоним:

sudo apt install python-is-python3
Чем отличается запуск через hsrp2vrrp.py от прямого?
Лаунчер hsrp2vrrp.py валидирует конфиги и скрипты, показывает меню, запускает нужный скрипт через subprocess и возвращает управление. Прямой запуск работает так же, но без проверок и меню. Результат генерации идентичен.
Что делать, если лаунчер не находит конфиги?

Экспортируйте конфиги в текущую папку:

ssh admin@core1 "show run" > core1.txt
ssh admin@core2 "show run" > core2.txt

Либо передайте пути аргументами:

python3 hsrp2vrrp.py /path/core1.txt /path/core2.txt
Что делать, если ключи HSRP на ядрах различались?
Скрипт migrate_to_vrrp2.py игнорирует исходные ключи HSRP. Вы вводите единый ключ, и он применяется к обоим ядрам.
