О проекте

Набор инструментов для планируемой миграции протокола резервирования первого хопа с HSRP на открытый VRRP.

Проект решает задачу плановой миграции FHRP на паре ядерных коммутаторов Cisco. Задача типична при переходе на вендор-независимую архитектуру, унификации политики FHRP в смешанной инфраструктуре и подготовке к миграции на сторонние платформы (Arista, Juniper, Huawei, NX-OS).

Инструмент автоматически анализирует две конфигурации show running-config с ядер core1 и core2, находит общие VLAN, группы HSRP, VIP, приоритеты и track-объекты, определяет роли active/standby по правилам RFC 2281 и генерирует последовательность команд VRRPv2 или VRRPv3 в порядке, минимизирующем простой хостов.

В комплекте — обёртка hsrp2vrrp.py: проверяет окружение (наличие конфигов и дочерних скриптов), отображает интерактивное меню выбора версии и возвращает управление по завершении миграции.

Шаг 1
Standby-ядро

Применяется первым. Временно становится мастером.

Шаг 2
Active-ядро

Возвращает мастер-роль через preempt delay.

Шаг 3
Проверка

Верификация и переход к следующему VLAN.

Быстрый старт

Клонируйте и запустите за пару минут.

Способ 1 — универсальный лаунчер (рекомендуется)

bash 
# Clone the repository
git clone https://github.com/landev-ru/hsrp2vrrp.git
cd hsrp2vrrp

# Run the launcher: validates configs, opens the menu
python3 hsrp2vrrp.py

Способ 2 — напрямую

bash 
# VRRPv2 (with auth selection)
python3 migrate_to_vrrp2.py core1.txt core2.txt

# VRRPv3 (no auth)
python3 migrate_to_vrrp3.py core1.txt core2.txt

На выходе появится файл migrate_vrrp2_sequential.cfg или migrate_vrrp3_sequential.cfg.

Стратегия миграции

Пошаговый сценарий на один VLAN. Повторяется для каждого VLAN, начиная с наименее критичных.

1

Подготовка (без изменений)

  • Снимок baseline: show standby brief, show ip ospf neighbor
  • Проверка ACL: пропуск IP-протокола 112 на 224.0.0.18
  • Проверка show vrrp brief
  • Согласование окна для критичного сегмента
2

Применение блока Standby

  • Войти на standby-ядро, применить блок
  • show vrrp brief — standby в статусе Master
  • ping VIP с хоста — стабильно (1–3 потери)
3

Применение блока Active

  • Войти на active-ядро, применить блок
  • show vrrp brief — active в статусе Master (приоритет 110 > 105)
  • Preempt delay 180 — в течение 3 минут возможен Backup
4

Верификация и документирование

  • Роли VRRP совпадают с pre-migration HSRP
  • Все track-объекты Up
  • OSPF-соседство восстановлено
  • Результат зафиксирован в журнале изменений

Не параллелить VLAN

Мигрируйте VLAN поочерёдно. Пакетное применение всех блоков одновременно приведёт к длительному разрыву на всех сегментах.

Проверка и откат

Чек-лист post-migration verification и критерии, при которых обязателен откат.

Чек-лист верификации

Проверка Ожидание
show vrrp briefActive — Master, Standby — Backup
ping <VIP>0% loss после стабилизации
show trackВсе объекты Up
show ip ospf neighborFull/2-Way по ожидаемым интерфейсам
show ip arp <VIP>MAC 0000.5e00.01xx

План отката

Применяется на уже мигрированном VLAN. Обратный порядок: сначала standby, затем active.

interface VlanX
 no vrrp <group> ip <VIP>   ! v2
 ! or
 no vrrp <group> address-family ipv4 ! v3
 standby <group> ip <VIP>
 standby <group> priority <orig>
 ip ospf cost <orig>

Критерии обязательного отката:

  • VIP недоступен > 60 сек после стабилизации preempt
  • Track-объекты Down > 5 минут
  • OSPF-соседство не восстанавливается
  • Потери через VIP > 1% в течение 5 минут

FAQ

Почему команда python не найдена?

Используйте python3 либо установите псевдоним:

sudo apt install python-is-python3
Чем отличается запуск через hsrp2vrrp.py от прямого?
Лаунчер hsrp2vrrp.py валидирует конфиги и скрипты, показывает меню, запускает нужный скрипт через subprocess и возвращает управление. Прямой запуск работает так же, но без проверок и меню. Результат генерации идентичен.
Что делать, если ключи HSRP на ядрах различались?
Скрипт migrate_to_vrrp2.py игнорирует исходные ключи HSRP. Вы вводите единый ключ, и он применяется к обоим ядрам.
Почему в VRRPv3 нет аутентификации?
RFC 5798 не предусматривает механизмов аутентификации. Компенсируйте ACL на ff02::12 и сегментацией.
Как переносятся track-и?

Скрипт находит строки standby <group> track ... и сохраняет всё после track:

  • VRRPv2: vrrp <group> track <...>
  • VRRPv3: track <...> внутри address-family ipv4

Поддерживаются object-tracking (track 1 decrement 20) и interface-tracking (track GigabitEthernet0/0 10).

Можно ли применить всё сразу, не по одному VLAN?
Технически — да, но это приведёт к длительному разрыву на всех сегментах одновременно. Применяйте поочерёдно.
